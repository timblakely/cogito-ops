01Three layers, two operators, one confusing noun

The apparent CRD redundancy is three separate systems whose vocabularies collide on the word “model”. Nothing is duplicated; one deploys weights, one publishes routes, one is the gateway.

llmkube (defilantech/LLMKube, group inference.llmkube.dev) owns two kinds. A Model is where the GGUF comes from plus a hardware target; an InferenceService is the llama.cpp server pod — args, GPU claim, probes, Service. It knows nothing about LiteLLM.

litellm-operator (home-operations/litellm-operator, group litellm.home-operations.com) owns LiteLLMProxy, LiteLLMModel, LiteLLMVirtualKey, plus guardrail and MCP kinds. It exists to replace one hand-edited config.yaml ConfigMap: the proxy renders config from whichever LiteLLMModels bind to it and stamps a config-hash annotation so the Deployment rolls only when the rendered output actually changes.

litellm itself is not an app folder in the usual sense. There is no HelmRelease — the workload is litellmproxy.yaml, which carries image, replicas, env and probes directly. The rest of the directory is CRs, dashboards, an ExternalSecret, an HTTPRoute and alert rules.

What auto-registration will and will not assert

The projection is deliberately conservative. It sets params.model to openai/<modelRef>, trims the endpoint to its /v1 root, uses a placeholder API key, and pulls maxInputTokens from the parsed GGUF context length. Capability flags LiteLLM cannot infer — function calling, vision, prompt caching — are left unset rather than guessed, and pricing is never invented. That single design decision is why hand-written models still exist alongside it.

02Why GPU manifests live in the litellm folder

llmkube's CRDs are cluster-scoped and there is no llmkube-models Flux Kustomization. Each model's two CRs therefore live in the folder of the app that consumes it, so that app's existing Kustomization reconciles them. llmkube/ holds only the operator, a PriorityClass and shared ResourceClaimTemplates.

The split between the two groups of files is not cosmetic. The flat llama-*.yaml files are a hardware switchboard: llama-nvidia.yaml and llama-nvidia-muse.yaml declare CRs with the same name, and four Strix files share one ResourceClaimTemplate. Which lines are commented in kustomization.yaml is the statement of what is loaded on which card. Burying that behind a second kustomization would hide the one decision an operator changes most often.

models/ is the opposite: roughly 30 of its 34 entries are external SaaS endpoints that deploy nothing at all, and auto.yaml has no backend whatsoever. They earn their own directory because they are catalogue, not placement.

06The auto router: rubric, tiers, and the broken hop

model: auto_router/complexity_router selects litellm's rule-based complexity router, not the embedding-based semantic auto_router. It runs as a pre-routing hook inside deployment selection: classify the prompt into one of four canonical tiers, then swap in that tier's model.

By default classification is local and free — seven weighted dimensions summed into a score, cut at 0.15 / 0.35 / 0.60. Jory sets classifier_type: llm, which replaces the scorer with a real LLM call constrained to {"tier": …} by response format.

What the classifier is actually told

Judge the intellectual difficulty of answering correctly, not how short the request is.

SIMPLE — greetings, chitchat, or factual lookups with a short known answer. Do not use this tier for unsolved problems, proofs, deep theory, multi-step analysis, or non-trivial code, even if the request is only one sentence.

MEDIUM — everyday requests that need some explanation, light reasoning, or minor code/technical content.

COMPLEX — non-trivial code, architecture, multi-step technical work, or specialized domain depth.

REASONING — open-ended analysis, proofs, famous hard problems, step-by-step reasoning, tradeoffs, or anything where a correct answer requires careful thought.

It also receives a trust-boundary paragraph declaring the caller's quoted system prompt and prior turns to be material to judge and never instructions. Its input is the current ask, the caller's system prompt, and by default the last three user turns truncated to 200 characters each.

If the classifier worked

SIMPLE would be the 3090's Qwen 3.8 and nothing else — and the rubric works hard to keep code off that tier. Since opencode's default model is auto, a working classifier would push essentially all of its coding traffic to MiniMax and the pools while leaving the local card handling greetings. Whether that is the intent is a question for Jory; it is not what the hardware layout suggests.

Prompt-cache economics — the latent cost bomb

The paid entries declare their cache spread explicitly: MiniMax-M3 reads cache at 6.0e-08 against 3.0e-07 input (5×), and reasoning-pool-1 at 2.0e-08 against 2.0e-07 (10×). A tier switch invalidates the provider-side prefix and re-pays creation rates on the new provider. Classification judges the current message, so ordinary agent sessions oscillate: “yes, continue” reads SIMPLE, the next ask reads COMPLEX.

Litellm's mitigation is exactly the one configured — session_affinity: true, TTL 3600, carrying a deployment pin because “a session frozen onto one model group but load-balanced across its deployments would still go cache-cold”. But the pin needs a resolvable session id, read only from metadata.session_id / litellm_metadata.session_id. Jory plumbs that in exactly one place:

# litellm/httproute.yaml — the EXTERNAL Envoy route only
requestHeaderModifier:
  set:
    - name: x-litellm-session-id
      value: '%REQ(x-session-id)%'

Every in-cluster consumer bypasses that route and posts straight to http://litellm.llm:4000/v1 with no such header — opencode, openclaw, hermes, foreman. No session id means the flag is inert, documented upstream as exactly that.

The coupling worth flagging

The broken classifier is currently what keeps costs flat: every request lands on one MiniMax-M3 deployment, so the prefix cache stays warm. Fixing the classifier without also plumbing session ids is what would trigger the blow-up — per-turn tier flapping across paid providers on a growing context. The two changes are coupled, and the coupling is invisible from either file.

Two smaller notes. litellmSettings.cache: true with Redis and ttl: 300 is a response cache keyed on the request — it looks like it addresses this and does not, since agentic traffic essentially never repeats verbatim. And one thing is defended: opencode declares "auto": { "limit": { "context": 140000 } }, the smallest tier member's window, so a client cannot push a 500k context into a router that might land on the local model.

07The fallback graph, and where it dead-ends

Three distinct things in this config look like “a model referring to a model”, and only one of them is:

  1. Shared modelName — not a reference. Several entries answering to one name form a model group. The other field, params.model, is the provider-side name and is never resolved against litellm's own list.
  2. order — priority inside one group. Selection filters to the lowest order value present.
  3. routerSettings.fallbacks — group to group, on error. The only genuine name-to-name reference, alongside the auto router's tier map.

Order levels are compiled into the fallback list

They are not separate mechanisms. When a group exhausts retries, litellm reads original_model_group = kwargs["model"], collects the group's order values, and synthesises entries for the untried levels, prepending them to the declared fallbacks:

order_fallback_entries = [{"model": original_model_group, "_target_order": o}
                          for o in order_values if o > skip_up_to]
combined_fallbacks = order_fallback_entries + external_fallback_group

Each target is then dispatched through run_async_fallback, which sets kwargs["model"] and calls async_function_with_fallbacks recursively — so the next group's own retries, order levels and fallbacks all apply. Depth is bounded by max_fallbacks (default 5, not overridden), and an attempted_targets set threaded through the whole walk skips anything already tried, which is what stops the deliberately circular llama-strix ⇄ llama-nvidia pair from ping-ponging.

Why auto never reaches skirk

The fallback machinery keys on kwargs.get("model"), and the complexity router's rewrite happens inside async_get_available_deployment via a PreRoutingHookResponse — it never writes back to kwargs["model"]. A request to auto therefore keeps the group name auto for fallback purposes and uses auto: [dsv4f, MiniMax-M3-chat]. The llama-nvidia → llama-strix entries fire only for clients that ask for llama-nvidia by name. The SIMPLE tier consequently has no local backstop: if the 3090 is preempted by a game session, an auto request classified SIMPLE goes to opencode zen, not to the Strix box sitting idle next to it.

09What this means for cogito, as things stand

Cogito's LLM stack uses the same two operators and reaches deliberately opposite conclusions, for reasons its own README already documents. The useful transfer is not architecture — it is one class of bug.

The structural difference that governs everything else

Do not adopt

  • The complexity router. On a swap pool it is pathological: a SIMPLE/COMPLEX oscillation across two pool members is a swap storm, and each swap fails held requests with 503 + Retry-After once swapBudget: 1800s is exceeded. If it were ever wanted, the only safe tier map is one whose members are all simultaneously reachable — that is, the resident local model plus the frontier tier, never two pool members.
  • Auto-registration. Already off, and the models README gives two correct reasons: projection deletes on Stopped, which is the normal state of ten of eleven services, and it points apiBase at each InferenceService directly, bypassing ModelRouter and handing clients a backend the pool can scale away mid-request. Jory's cluster hit the third cost the README predicts — projected names become client-facing names.

Worth considering

  • A narrow fallback to the frontier tier. routerSettings currently declares only num_retries: 2 and timeout: 1900, so a swap-budget 503 surfaces to the client after two retries. A fallbacks entry mapping local aliases to planner-gpt would give a real escape hatch, since the frontier models are remote and always available. Two caveats, both from this teardown: an accidental fallback bills OpenAI, so scope it to the aliases where that is acceptable; and do not add a context_window_fallbacks map unless every group is in it, because a partial map removes the generic fallback rather than supplementing it. Superseded by §11: the escape hatch shipped as the role-level worker → worker-escalated fallback — seated on GLM 5.3 in The Idle Bench §6 — rather than a blanket map onto planner-gpt.
  • Extend the role-alias precedent. gemma4-agentic already points at openai/gemma-4-31b-google-qat under a stable role name — the pattern that would have spared Jory the dsv4f leak. Client-facing HF identifiers like Vishva007/Qwen3.8-27B-W4A16-AutoRound are honest but couple every consumer and virtual-key scope to one exact quant; a role alias beside them lets the quant change without touching clients.

The one refactor both repos need

A CI check that every model name reference resolves. Finding one and the trap cogito's own open-webui.yaml already documents — “a scope naming a model that does not exist blocks the key SILENTLY rather than erroring” — are the same bug: an unvalidated string that must match a modelName. One script over the rendered kustomize output covers every instance of it.

Concretely, build the set of valid modelNames and assert that each of these resolves into it:

  • every entry in a LiteLLMVirtualKey.spec.models list — the silent-scope trap, live in both repos;
  • every fallbacks, context_window_fallbacks and content_policy_fallbacks target;
  • every complexity-router tiers value, complexity_router_default_model, and classifier_llm_config.model — finding one, caught by three lines of script;
  • every model name hardcoded in a consumer ConfigMap or HelmRelease env (WIKI_MODEL, MODEL, foreman agent providerConfig.model, the opencode and openclaw pickers).

Two structural assertions belong in the same script, and both are cheap:

  • No dangling backends. Any LiteLLMModel whose apiBase names an in-cluster Service must have a matching InferenceService in the same rendered output — finding three, and it fires on a commented-out line, which is exactly when a human misses it.
  • Advertised context must match the backend. Cogito's README calls the maxInputTokens ↔ maxModelLen/contextSize mirror “a standing maintenance cost rather than a bug to fix” — that is a diff, and a diff is testable. The same assertion applied to a multi-member group would have caught the 1M-versus-262k mismatch behind finding four.

10The target state: one local model, nothing swaps

Section nine analysed cogito as it is — one resident model chosen from an eleven-member swap pool. The target is narrower than that analysis assumed: a single local model, Qwen 3.8 27B at FP8, spanning both 3090s, with the KV pool spent on concurrent seats rather than a maximal per-sequence ceiling. That one endpoint serves several agents at once, so a second local model is no longer needed to get a second lane — Muse Glimmer becomes optional rather than pending. Everything else falls out of the catalogue.

Revised after the capacity plan

This section and the next were first written with the endpoint tuned as it ships — two seats at a 262k ceiling. The Idle Bench re-derives the numbers for a coordinator actually fanning out subagents, and four of its conclusions land back here: the per-seat ceiling drops to 131k to fund about six concurrent seats (§2 there); vision leaves the 3090s entirely (§4); Muse's landing spot is the preemptible utility node (§3); and the cloud seating puts Luna at the coordinator, GLM 5.3 at worker-escalated, and K3 at reviewer-escalated (§6). The text below is updated in place; this callout exists so the delta stays visible to anyone who read the earlier version.

Why only one model on two cards

The arithmetic decides it. Qwen 3.8 27B at FP8 is roughly 27GB of weights, which does not fit a 24GB card — hence tensorParallelSize: 2 across both. Muse Glimmer is 17GB (the size is in its filename). Two 3090s are 48GB, so holding both leaves about 4GB for every KV cache on the node, which defeats the point of the exercise. One model with a large context beats two models with none.

Parallel agents on one endpoint — shipped at two seats, retuned to six

The mechanism does not need building — the manifest already sets --max-num-seqs: 2, and three neighbouring settings make that number mean something. What changes is the sizing: the shipped values serve two long interactive chats, and the capacity plan re-spends the same pool on six worker seats.

The mechanism is vLLM's continuous batching: scheduling happens per iteration rather than per request, so every forward step batches whatever sequences are runnable at that moment instead of running one request to completion before starting the next. Four settings in qwen-3-8-fp8 govern it, and they are all already on:

SettingTodayTargetWhat it does
--max-num-seqs26 sweep to 8Cap on sequences batched concurrently. This is literally the parallel-agent count
--max-model-len262144131072The per-seat ceiling. KV cost is linear in tokens held, so halving it roughly doubles the full-length seats the pool holds — and the coordinator keeps long context in the cloud, so no local consumer should miss it. maxInputTokens mirrors it in the same commit
enableChunkedPrefilltruekeepSplits a long prefill into chunks interleaved with other sequences' decode. Without it, one agent submitting a 100k-token prompt stalls the others for the entire prefill — which is what makes concurrency feel real rather than nominal
enablePrefixCachingtruekeepConcurrent agents sharing a system prompt and tool definitions share KV blocks, so the Nth one's prefill is largely a cache hit — it earns more as the seat count rises, not less
maxNumBatchedTokens8192keepPer-step token budget across the whole batch

It costs less than it sounds because decode is memory-bandwidth bound, not compute bound. Reading the weights for one forward step costs the same whether one sequence or eight are riding along, so a second concurrent sequence adds very little per-token latency while nearly doubling aggregate throughput. That is the whole reason batching works, and why one endpoint serving two agents is not the same as two agents splitting one agent's worth of capacity.

What it actually trades against

KV cache, not compute. Every concurrent sequence carries its own, and maxModelLen: 262144 is the per-sequence ceiling — two agents both at full context need twice the pool. The current --max-num-seqs: 2 is very likely sized to exactly that: the KV pool left after ~27GB of FP8 weights holds about two sequences at the advertised length.

vLLM degrades gracefully rather than failing — when blocks run out it preempts and requeues rather than erroring — but a preempted sequence is recomputed, which is a latency cliff rather than a gentle slope. So raising the cap above 2 is free only while the concurrent sequences are short. The real budget is max_num_seqs × realistic context against the KV pool, and “realistic” for a subagent is far below 262k. Subagent prompts are short and self-contained — that is the whole point of the coordinator shape in section eleven — so the capacity plan commits to the trade rather than leaving it hypothetical: ceiling 131072, cap 6 swept toward 8, maxInputTokens mirrored to 131072 in the same commit, and an rpm / parallel-request limit on the worker key a notch above the seat count, so a coordinator that fans out twelve subagents queues at the proxy with clean per-key errors instead of stacking silent timeouts inside vLLM's scheduler. The arithmetic, and the seat-sweep benchmark that replaces it with data, are The Idle Bench §2 and §7.

One interaction to watch

This build runs --speculative-config {"method":"mtp","num_speculative_tokens":3}. Speculative decoding pays off most at low batch sizes, where the accelerator has idle capacity to verify draft tokens almost for free; as concurrency rises and the GPU saturates, the benefit shrinks. Two concurrent agents sat comfortably in the range where both mechanisms help; six seats does not obviously, so the retune carries its benchmark with it — MTP on and off at max-num-seqs 6, keeping speculation only if it still earns its verify-compute at real concurrency rather than assuming the two optimisations compose.

What this does and does not settle about Muse

It settles the capacity question completely. If the reason to want a second local model was to run a reviewer alongside a worker without them queueing, that reason is gone — one Qwen endpoint does it today, and the two roles are just two aliases with different reasoning_effort.

It does not touch the capability question. Muse Glimmer is an uncensored creative model; concurrency does not make Qwen into one. If Muse was wanted for what it writes rather than for the lane it occupies, that reason survives untouched and still needs its own card — and it now has one on paper: a re-quant small enough to leave KV headroom on the preemptible 5070 Ti, in the utility roster of The Idle Bench §3. Worth being deliberate about which of the two motivated it, because only one of them has just been answered.

The alternative: one model per card

Decided — the target stands

On 2026-08-21 the choice landed on FP8 across both cards, without running the benchmark below. The alternative stays written down as the recorded fallback if TP2 throughput ever becomes the constraint that matters, not as an open question.

The other way to spend 48GB is to give each card a whole model and keep both resident permanently. It is worth writing down because the trade is not one-sided, and one of its costs is not the one people expect.

The quant is chosen for you. Of the three Qwen 3.8 builds already published, only one fits a 24GB card:

The throughput row is the one that might surprise

Cogito's own manifest records that the two 3090s have no NVLink, so tensor-parallel workers exchange activations across PCIe, with an all-reduce at every layer. That is a real and well-known throughput tax on consumer cards. It is entirely possible that 4-bit on a single card is faster in tokens per second than FP8 split across two, even though it is the lower-quality build — which turns the choice into quality-and-context versus latency rather than a straight downgrade. Neither direction should be assumed: this is a benchmark, not an argument, and it is cheap to run because both builds are already staged. That benchmark is now deliberately deferred — the decision landed on FP8 without it, trading a possible latency win for settled quality and context. If it is ever run, one rule from §12 applies: match the KV cache dtype across both arms — the strix FP8-vs-Q4 A/B initially measured a 4-bit V cache rather than the weights, and had to be redone at q8_0 on both sides.

And the device-plugin fix stops being optional

Under the target there is one pod on the node, so however the plugin hands out its eight time-sliced replicas, that pod is alone on the hardware. Under the alternative there are two pods each requesting one unit, and time-sliced replicas of the same physical GPU are interchangeable to the scheduler — so both models can be handed slices of the same card while the other sits idle. That is not a subtle degradation; it is two 30B-class models contending for 24GB. Setting replicas: 1 so the advertised count is the physical count is a prerequisite for this layout, not a tidy-up.

1 · Make the GPU unit count truthful

Cogito's nvidia-device-plugin time-slices with replicas: 4, so iggy advertises eight units for two cards. The single remaining local model is tensor-parallel and therefore needs two distinct devices — the two 3090s have no NVLink and workers exchange tensors over shared memory — while a request for two time-sliced units is not guaranteed to span two cards. It evidently works today, so the plugin is handing out distinct devices in practice; that is worth confirming with nvidia-smi -L and CUDA_VISIBLE_DEVICES inside the running pod, and then pinning by setting replicas: 1 so the advertised count is the physical count. With one model on the node this is the only correctness property left that depends on the plugin's allocation order — and under the alternative above it is a prerequisite rather than a precaution.

2 · Delete the swap machinery outright

With nothing to swap, an entire layer goes away rather than being retuned:

  • ModelPool — default, swapPolicy: sticky, swapBudget: 1800s and its eleven members. All of it.
  • ModelRouter — with a single backend there is nothing to dispatch between. BackendNameMatch was earning its keep across eleven backends and one resident member; against one always-on InferenceService the catalogue can point apiBase straight at its Service and remove a hop and a component. The cost is losing the modelName-to-slug indirection, which the role aliases in section eleven replace anyway.
  • routerSettings.timeout: 1900 — chosen to exceed the swap budget. With a resident model it means a hung backend hangs the client for 32 minutes. Bring it down to a real inference ceiling.
  • num_retries: 2 — its comment explains it approximates the swap wait for a 503 plus Retry-After that ModelRouter will no longer emit. The count is still reasonable; the reasoning behind it is not, so rewrite the comment or someone will preserve the number for the wrong reason.
  • rbac-prefetch.yaml — supplementary RBAC for Model.spec.prefetch. Harmless, and it guards a genuinely quiet failure, but with pvc:// sources and no swapping there is nothing left to prefetch.

3 · The cache is already simpler than its documentation

The two-tier hot and cold cache reads as significant overhead, and it is worth knowing that in the manifests it is not. Every Model.spec.source is pvc://llmkube-model-cache/… — the hot NVMe PVC. Nothing references llm-model-archive; that NFS PV is declared and reconciled but no source traverses it. The “cold to hot copy on first serve” the README describes is not what happens: the weights were staged onto the hot PVC out of band and the operator mounts them read-only.

So simplification here is mostly deleting a mental model:

  • Stop calling it a cache. With no eviction, no swapping and two models ever, it is storage. That removes the working-set sizing, the “must hold every model simultaneously or swaps fail on a full disk” caveat, and any need for llmkube cache clear.
  • The 450Gi sizing is now wrong by an order of magnitude — it was computed for ten models totalling ~336GiB, against a target of roughly 45GB. Worth knowing that PVCs generally expand but do not shrink, so reclaiming it means a new PVC and re-staging the weights. On a 932GiB NVMe that may not be worth the churn; the number being wrong in the comment is worse than the space being allocated.
  • Keep the NFS archive, demote it in the docs. It is a pre-existing NAS share costing nothing incremental, and it is the only off-node copy of weights that would otherwise need re-downloading. It is a backup, not a tier.

4 · Shrink the catalogue, and move the key scopes in the same commit

Nine local aliases lose their backends. Their LiteLLMModels, Models and InferenceServices all go, and the open-webui virtual key currently scopes eight of them by name. Its own comment records why that has to move together: “a scope naming a model that does not exist blocks the key SILENTLY rather than erroring”. This is the exact failure the validator below exists to catch, and it is about to be triggered deliberately.

One capability leaves with them: the retiring Gemmas were the catalogue's only vision models, and nothing on the target endpoint replaces them. Deliberately so — rare vision should not hold 3090 VRAM hostage, and the answer is tiered off the worker GPUs entirely: a small VLM running wholly on kristeva's CPU (llama.cpp keeps the projector there via --no-mmproj-offload, and image encode on 40 threads is seconds — fine for occasional screenshots), the compact VLM on the 5070 Ti when no game holds it, and the cloud tier for genuinely hard vision. The sizing and the tiering are The Idle Bench §4.

5 · Keep auto-registration off, for a different reason than before

The models README gives two reasons it must stay off, and this plan removes both: nothing sits in Stopped any more, and pointing apiBase at an InferenceService no longer risks a backend the pool can scale away mid-request. The third reason survives and is now decisive on its own — projected models are named after the InferenceService, so client-facing names become deployment names, which is precisely what section eleven's role aliases exist to prevent. Rewrite the README's stated reasons, or the next reader will correctly conclude the ban lapsed with the pool.

6 · Routing is superseded — see section eleven

An earlier version of this plan asked whether always-on models finally made the complexity router viable here. That question is closed: a per-request classifier is the wrong shape for a deliberately hybrid cloud-and-local cluster, for reasons section eleven sets out. What replaces it is a coordinator that delegates, and it removes rather than adds routing configuration.

7 · What the validator must now assert

  • Every alias named in a virtual-key scope, a consumer ConfigMap, or a fallback chain resolves to a published modelName — the check that would catch step four going wrong.
  • No LiteLLMModel points at an in-cluster Service with no matching InferenceService in the same rendered output.
  • maxInputTokens matches the backend's maxModelLen — concretely, 131072 on both sides once the seat retune lands. With one model this is a two-line check, and it is the assertion that keeps the advertised context honest through exactly that kind of retune.

Section eleven adds the role-alias assertions.

11The coordinator pattern, and why it beats autorouting here

The routing plan assumed something this cluster is not: a single cost domain. A per-request classifier is a reasonable optimiser when every candidate sits on the same premises and a wrong guess costs only prefill time. Across a cloud-to-local boundary each switch costs money at cache-creation rates, and the guess is made before the work exists. Delegation replaces prediction.

Four reasons the boundary changes the answer

  1. The expensive axis is the cache boundary, not the token price. Section six put numbers on it — 5× for MiniMax, 10× for Luna between a cache read and a fresh input token. A classifier flapping between tiers re-pays creation rates at every crossing, and the mitigation LiteLLM ships for it needs session ids the clients do not send. A coordinator is the session: it holds one long-lived prefix at one provider, so cache locality is structural rather than something a flag has to defend.
  2. Classification happens before the work exists. Part two's coding loop reaches the same cost goal with no classifier at all — grooming answers only ready or not-ready, and escalation follows attempts that actually failed. A coordinator goes one better: it escalates having read the subagent's output.
  3. A per-request classifier cannot see task structure. “Update these three HelmReleases and explain what changed” is one request that wants a mechanical model for the edits and a reasoning model for the explanation. A router must pick one. A coordinator splits it.
  4. The router's failure mode is silent. Finding one is exactly that shape: a name that does not resolve degrades to a default model behind a log warning. Delegation failures surface as tool errors inside a conversation somebody is reading.

Home-ops has already converged on this

This is not a hypothetical alternative to the router — it is the shape the same cluster settled into where the work actually happens. The openclaw config declares three named agents with per-role models, per-role thinking defaults, and per-role fallback chains, plus a spawned-subagent tier:

AgentPrimary modelThinkingToolsRole
Saffron reasoning-pool cloud high full — exec, write, browser, sessions_spawn, toolhive The coordinator. The only agent that can spawn subagents
Miso glm-5.3 cloud adaptive default plus memory The default conversational agent
Matcha dsv4f cloud low restricted — no write, no spawn Cheap, fast, read-mostly worker
subagents dsv4f cloud high inherited maxConcurrent: 3, archived after 120 minutes
heartbeat llama-nvidia local reasoning off direct policy allow Hourly, lightContext, isolatedSession — never touches the main prefix

Three details are worth lifting directly. Thinking level is set per agent, not per model — low for the restricted worker, high for the coordinator and its subagents — which is the same knob argued for below, already in production. The recurring background task is pinned to the local model in an isolated session with includeReasoning: false, so routine work never enters the expensive conversation's context. And the coordinator's growing prefix is managed explicitly rather than left to grow: compaction with a 30k reserve floor and a memory flush at 80k tokens that writes decisions out to a dated file.

Two differences from the plan sketched here, both driven by hardware rather than preference:

  • Home-ops' workers are cloud, its local models are the floor. Every agent's fallback chain ends the same way — cloud primary, then cheaper cloud, then llama-nvidia, then llama-strix. Local capacity is the free backstop underneath, not the default worker. That follows from the hardware: one 3090 running a single 27B tenant that games can preempt, and a Strix box shared with a reranker, an embedder and image generation. Cogito's two 3090s can be dedicated to worker traffic, which is what makes local-first workers plausible there and not here.
  • The fallback chains live in the client, not the proxy. Each agent declares its own ordered list in openclaw's config rather than relying on routerSettings.fallbacks. That gets per-role fallback without per-role proxy configuration — but it also means two fallback mechanisms can fire on one request, and only the proxy's half is visible in the LiteLLM dashboards. Worth choosing one layer deliberately rather than inheriting both.

Read against section six, this reframes the auto router: the heaviest agentic consumers here — openclaw explicitly, and opencode by default — either bypass tier routing entirely or point at a single alias. A classifier that has never routed a request has evidently not been missed.

What the LiteLLM config becomes

1 · Role aliases, not model identifiers

Publish coordinator, worker, reviewer, worker-escalated, reviewer-escalated as modelNames over concrete backends — the gemma4-agentic precedent generalised — and, once the A380 retrieval floor lands, embedder and reranker beside them over /v1/embeddings and /v1/rerank (The Idle Bench §4). Swapping the worker quant then touches one file rather than every consumer config and key scope. The Hugging Face identifiers can stay published alongside for direct use from Open WebUI.

2 · One virtual key per role

This is where the coordinator pattern beats autorouting most decisively, and it is not about quality. Under a single auto alias every request enters the proxy identically and nothing downstream can attribute spend or intent. With a key per role, LiteLLM's per-key accounting answers “what did delegation cost this week” for free — and because the local entries declare input_cost_per_token: 0, free and billed separate themselves in the existing dashboard. Part two's foreman key, scoped to exactly the three models its agents use, is the pattern to copy: a worker key that permits only worker means a harness bug cannot spend money.

3 · Fallbacks by role — and deliberately asymmetric

worker: [worker-escalated] is exactly right, and it is cheap precisely because worker prompts are short and self-contained: a cold prefix on the escalation target costs almost nothing. The coordinator should carry no cross-provider fallback at all — its prefix is the entire conversation, so failing it over re-pays creation rates on a very large context for a request a retry would probably have served. That asymmetry falls straight out of the cache numbers in section six and is invisible without them. Whatever is chosen, remember section seven: a partial context_window_fallbacks map removes fallback rather than adding it, so cover every role or set none.

4 · Timeouts by role

The coordinator wants a long ceiling — it thinks for a while and that is the point. The worker wants a tight one, because a fast worker failure is what makes escalation feel responsive. One global timeout: 1900, inherited from the swap budget, serves neither.

5 · Thinking level is a role knob, not a model property

The Qwen 3.8 entries already expose reasoning_effort through allowed_openai_params and declare low / medium / xhigh. Mechanical worker turns — a yaml edit, a bash invocation, a file read — want low: thinking tokens are latency multiplied by turn count, and there are many turns. Review turns want medium. That is a sufficient reason for worker and reviewer to be separate aliases even when they point at the same InferenceService.

6 · Everything the router needed simply does not arise

No auto entry, no classifier model to resolve, no tier map to validate, no session-id plumbing through Open WebUI, Hermes and pi. Findings one, two and five in section eight are prerequisites that this design never incurs.

What it changes about the hardware plan

  • Both worker roles live on one endpoint. The coordinator is in the cloud, so both 3090s serve subagents — but as a single tensor-parallel Qwen instance, not as two smaller models. worker and reviewer are two LiteLLMModel aliases over the same apiBase, differing in reasoning_effort, and their concurrency comes from --max-num-seqs and continuous batching. The capacity plan sizes it: six seats at a 131k per-seat ceiling, with a 2 → 8 sweep in The Idle Bench §7 to replace the estimate with measurement.
  • The FP8 build already has speculative decoding. An earlier version of this argued for lued/Qwen3.8-27B-INT8-W8A16-MTP on the grounds that speculative decoding cuts worker latency, which is multiplied by turn count. That trade does not exist: the FP8 repo ships mtp.safetensors and the manifest already runs --speculative-config {"method":"mtp","num_speculative_tokens":3}. The chosen build carries the same MTP head as its sibling, so there is nothing to give up here.
  • The preemptible node has no mandatory tenant — and now a planned utility roster. Muse Glimmer was going to be the second local lane; continuous batching removes that need, so the 5070 Ti hosts only tenants whose eviction costs a retry: a compact VLM, a Muse re-quant if it is still wanted for what it writes, Whisper, and an optional heavy reranker. See The Contested GPU for how the eviction works and for the two things about Muse's current configuration that will not fit a 16GB card, and The Idle Bench §3 for the roster and its rules.
  • Retrieval gets its own always-on silicon. The embedding and rerank floor lives on kristeva's Arc A380 — never on the preemptible node, so RAG does not silently break whenever someone streams a game — and vision leaves the 3090s entirely for the CPU, utility-node and cloud tiers. Both are The Idle Bench §4.
  • Nothing local backs anything else up. With one local endpoint there is no second local model to fall back to. The escalation path is entirely cloud, which makes the worker → worker-escalated fallback load-bearing rather than an optimisation.

What still has to be true

A reasoning coordinator is not a substitute for the rails part two documents — it changes which ones you need.

  • Ground subagent output deterministically wherever you can. Foreman requires its reviewer to quote the ask verbatim, list files from the real diff, and anchor findings to changed lines, because a 30B model's verdict is not trustworthy on its own. A local worker reporting “I updated the YAML” deserves a kustomize build and a diff, not a nod.
  • Cap turns and spend per subtask. Foreman's Agents carry maxTurns — 160 for coders, 80 for reviewers — plus stuck-loop detection with context soft and hard caps. A coordinator loop needs the equivalent, or a confused coordinator retries a failing subtask indefinitely at cloud rates.
  • Record why each escalation happened. The escalation log is the dataset that tells you whether the local model is actually capable of the work being handed to it — which is the question the whole design turns on, and the one a classifier can never answer because it never sees the outcome.

The validator changes shape

The checks proposed in sections nine and ten survive, with the tier assertions replaced:

  • every role alias resolves to a published modelName, and every virtual-key scope names only aliases that exist;
  • no role alias whose backend sits on the preemptible node appears without a fallback behind it;
  • the embedder and reranker aliases resolve to live backends once the retrieval floor lands;
  • the coordinator alias has no cross-provider fallback entry — an assertion that encodes the cache reasoning above, so a future edit cannot quietly undo it;
  • the dangling-backend and advertised-context checks are unchanged, and still catch the class of bug behind findings three and four.

12Addendum: the next seventy-two hours

This document reads home-ops at eed15dcc — a pin that aged fast. Within three days the alias layer was gone, the router's economics changed underneath it, and the coordinator this document argued for was running in two harnesses. The deltas, mapped to the sections they amend.

The alias layer is gone — and the trap fired on the way out

Commit cefbebe9 deleted seven hand-written LiteLLMModels and renamed every caller onto llmkube projection names (self-hosted → llama-strix, nvidia → llama-nvidia, …), explicitly accepting the trade §9 warns cogito away from: "model names are now deployment names, so swapping what backs a lane renames the model and moves every caller with it. Over the last two days that would have been three renames on the strix lane alone." On the way, the rerank rename left memini's virtual key scoped to a name that no longer existed — the silent-scope failure of finding one, fired in production. The fix (8f9c52fc) moves eleven virtual keys into git, with every scope entry checked against the rendered model_list — the validator §9 proposed, built independently three days later, after the failure it exists to prevent. Cogito keeps its aliases; the counter-experiment now has a documented body count on both sides of the trade.

drop_params: set globally, reverted in a day

The same refactor set litellm_settings.drop_params: true to absorb the deleted per-model additional_drop_params. It lasted twenty hours: b49d40c4 reverts it because it strips thinking from every request. Cogito's own qwen-3-8-fp8 manifest predicted this class of failure verbatim — "dropping params everywhere would have hidden exactly this class of mistake silently" — and Jory's glm-5.3 now carries the same per-model allowed_openai_params: [reasoning_effort] pattern instead.

The ladder learned economics

The Opencode Go plan behind §4's pools turned out to be dollar-metered — $60/month, $30/week, $12 per rolling five hours — and dsv4f was repriced roughly 8× mid-month with its own $15 sub-cap. The response (d22e42d9) inserted neuralwatt, an energy-priced PAYG provider, as a dsv4f backstop rung and as frontier-pool rung 5 (DeepSeek V4 Flash at $0.104/$0.207, with glm-5.2-flex at half its old price behind it). The resulting ladder is deliberately non-monotonic in price, with the commit stating the principle outright: "order encodes preference, not cost." The commit is equally honest about quality: the benchmark scores that would justify the floor came from a retired suite "measuring retrieval rather than real work," so the rung ships with a one-line revert path instead of a citation. Amends the group table in §4 and the flat-rate assumption behind §6's cost table.

The coordinator is no longer a proposal

Both opencode — now also an in-cluster server pod with SSO, a persistent home, and memini memory shared with the laptop — and pi carry a coordinator with five role subagents (explorer / fixer / fixer-bigctx / oracle / reviewer), the lane price model written into the coordinator's own prompt, and a council rule for high-stakes review: verdicts from different model families, never one model grading its own work. The role indirection deleted from the proxy re-appeared in the harness, where it absorbed two lane retargets in a week without touching a caller. The whole client half is the fifth companion, The Portable Coordinator — including the durable workflow layer that carries part two's rails into interactive work.

Foreman keeps tightening

Bridge 0.7.0 gives the local coder a second slot, coder-frontier moved off the MiniMax shim onto reasoning-pool, and the dispatch bridge now runs overnight only — time-partitioning the contended 3090 between interactive fixer traffic by day and the batch pipeline by night. That is a third answer to seat contention, alongside cogito's more-seats retune and the prompt-level "keep fixer jobs small" in the harness.

Two experiments concluded

  • ninfer-3090 is dead. The from-scratch CUDA engine claiming to beat llama.cpp on a 3090 was containerized (no Linux build existed upstream), given the card, and ditched within a day — leaving behind one useful by-product, a measured context ceiling of ~157k for Qwen 3.8-27B on that card.
  • The FP8-vs-Q4 A/B initially measured the wrong thing. The FP8 arm ran a 4-bit V cache; protocol adherence fell while single-shot reasoning held — the signature of instructions given early decaying over accumulated context — and the run was redone with KV matched at q8_0 on both arms before any conclusion. The generalisable rule, now recorded in The Idle Bench §7: match KV dtype across arms, or the benchmark measures the cache.
