01How a game session takes the GPU back

The whole mechanism is one negative number. Nothing on the gaming side knows the LLM exists — no high-priority class on the game, no cordon, no custom controller, no admission webhook.

The gaming stack is Games-on-Whales — Wolf plus the direwolf-operator, driven by User and App CRs, streaming to Moonlight clients. It shares ganyu's RTX 3090 with llama-nvidia. Four pieces make the handover work:

PieceConfigurationEffect
nvidia-device-plugin sharing.timeSlicing.resources: [{name: nvidia.com/gpu, replicas: 2}], node-affine to topology.kubernetes.io: egpu The one physical 3090 advertises 2 schedulable units
gpu-preemptible PriorityClass, value: -100, globalDefault: false Anything at default priority (0) outranks it — no annotation needed on the winner
llama-nvidia resources.gpu: 1 · priorityClassName: gpu-preemptible · rolloutPolicy.waitForIdle: false Holds one unit, and is the only evictable pod on the node
Wolf session wolf sidecar requests nvidia.com/gpu: 1, app container requests nvidia.com/gpu: 1, no priority class One session needs 2 of 2 units — the node's entire budget

That last row is the part that is easy to miss and easy to get wrong when copying this. A session claims the GPU twice — once for the compositor that encodes video, once for the application being streamed. Because that equals the whole advertised budget, there is no arrangement in which the session and the LLM coexist, so the scheduler must preempt. Advertise four units instead of two and the session would simply take two of them, leave the LLM running, and both would fight over the same silicon.

What it costs, and what does not work yet

  • Eviction is abrupt. The pod gets SIGTERM and in-flight requests die; there is no drain. rolloutPolicy.waitForIdle: false is the acknowledgement that this pod is not gracefully drained in general.
  • Restart is a disk read, not a download. Weights come back from the shared llmkube-model-cache PVC on CephFS, which is why the README treats a swap as cheap.
  • Video streaming does not work yet — sessions start and preempt the LLM, but produce no video. The README attributes this to the NVIDIA DRA driver injecting compute but not graphics userspace, and treats it as blocked on upstream. The comparison above suggests a closer and much cheaper explanation.

Worth separating those two facts when borrowing this: the preemption half is complete and proven; the streaming half is one testable configuration change away from a known-good reference, not blocked on someone else's code.

02The video blocker looks misdiagnosed

The blocker looks misdiagnosed

There is working prior art for this exact stack — Talos, Kubernetes, NVIDIA, Wolf — in shrinedogg/biggs.dog, whose images Jory is already running. Comparing the two clusters against games-on-whales/fenrir upstream turns up a much smaller candidate cause than an unfixable upstream gap.

The README attributes the failure to the NVIDIA DRA driver's CDI spec omitting the graphics userspace. But there is no NVIDIA DRA driver in this repo. The only DRA driver deployed declares gpu.amd.com and gpu.intel.com; every NVIDIA DeviceClass is absent. NVIDIA access on ganyu comes from somewhere else entirely:

# talos/main/controlplane/eGPU-schematic.yaml
- siderolabs/nvidia-container-toolkit-production     # CDI / container runtime
- siderolabs/nvidia-open-gpu-kernel-modules-production

# kube-system/nvidia-device-plugin — nvidia.com/gpu, timeSliced ×2

That is the container-toolkit path, not DRA. And it only engages for pods that ask for it. Upstream's NVIDIA example sets one field that Jory's adapted copy does not:

# fenrir/examples/nvidia_devices/firefox.yaml
  template:
    spec:
      runtimeClassName: nvidia          # ← absent from all three of Jory's Apps
      containers: [...]

Corroboration sits on the same node: llama-nvidia sets runtimeClassName: nvidia explicitly. If the NVIDIA runtime were the node's default, the inference pod would not need to. Without it the session pod runs under the default runtime, the nvidia-container-runtime hook never fires, and NVIDIA_DRIVER_CAPABILITIES=all on the wolf sidecar has nothing to act on — no driver userspace is injected, graphics or compute. That is precisely the reported symptom: Mesa fallback, failed to create dri2 screen, ZINK: failed to choose pdev, Failed to create EGLDisplay. It also explains the second finding, that /dev/dri never appears.

The honest caveat

biggs.dog's own App manifests also omit runtimeClassName, and its node-level Talos configuration lives in Omni ConfigPatches deliberately kept outside the repo — so that cluster may make the NVIDIA runtime containerd's default instead. Either way the fix is the same shape and one line to test: get the session pod onto the NVIDIA runtime, by RuntimeClass on the App template or by node default. This is a hypothesis with three pieces of supporting evidence, not a confirmed diagnosis — but it is testable in a minute, which is a very different proposition from waiting on kubernetes-sigs/dra-driver-nvidia-gpu.

03Getting video out of Wolf: lessons from a cluster where it works

biggs.dog's engineering notes read as a list of independent causes of a black screen, each found the hard way. Most are invisible until the one before it is fixed, which is what makes the order they are attacked in matter more than any single item.

Start with Test Ball, not Firefox

Both clusters ship the same three Apps, and one of them is a diagnostic instrument rather than a workload. Test Ball sets startVirtualCompositor: false and startAudioServer: false and supplies a raw GStreamer source:

video:
  source: |
    videotestsrc pattern=ball flip=true is-live=true !
    video/x-raw, framerate={fps}/1

It never touches EGL, wlroots, or an application's renderer — a synthetic pattern goes straight into the encoder. That bisects the failure cleanly. If Test Ball streams and Firefox does not, the fault is in the compositor and EGL path, which is exactly where the reported panic lives. If Test Ball also fails, the fault is upstream of it: device injection, the encoder, or the RTSP and UDP transport.

Before drawing any conclusion from a Test Ball run, fix an inconsistency in the manifest: Jory's Test Ball pins renderNode: /dev/dri/renderD128 while his Firefox pins renderD129. biggs pins renderD129 for both, commented “the dGPU's DRM node is renderD129”. A wrong render node does not error — Wolf fails GPU vendor detection and silently falls back to software x264, which still produces a picture. So a Test Ball that streams could be telling you the GPU works, or telling you the CPU does.

Four forked images, and what each one actually fixes

Jory already runs all four at equal or newer tags, so he inherits the fixes — but knowing what they fix is what makes a regression recognisable rather than mysterious.

ImageWhat upstream doesWhy it breaks in Kubernetes
moonlight-proxyWaits 25s on /launch for the session to come upA cold start is image pull + Wolf boot + agent readiness, well past 25s — upstream returns 500 just before the pod is ready and the client cancels. Fork raises it to 120s
direwolf-operatorReconciles the stream onceIf wolf-agent is not up on the first try the session stalls until the 1-minute reaper kills it. Fork retries, and prunes stale trackedSessions
wolf-agent—Implements Wolf's fake-udev in Go: writes /run/udev/data entries and broadcasts synthetic libudev netlink events inside the pod netns, so SDL and Steam see hotplugged controllers
wolfAdvertises both legacy wl_drm and dmabuf v4 feedbackNested wlroots binds both and aborts on the duplicate device announcement. Fork skips wl_drm when dmabuf v4 feedback is active

Two of the four are timeout fixes, and that is the generalisable lesson: porting a stack designed for one Docker host to Kubernetes breaks latency assumptions first. Image pull, scheduling and readiness gates insert seconds where the original design assumed milliseconds, and the resulting failures present as protocol errors rather than as slowness.

The GPU is injected per container, and only where asked

  • CDI injection is per allocated container. The app container needs its own nvidia.com/gpu request; without one it has no render node and streams black even though the wolf sidecar is fine. Both clusters do this correctly.
  • That is why the slice count is what it is. biggs time-slices into four: one for the tuning DaemonSet, one for vLLM, and two for the session's wolf sidecar plus app container. Jory slices into two — wolf plus app — which is precisely why a session consumes his entire budget and the LLM must be evicted. The slice arithmetic is a direct consequence of per-container injection.
  • Render nodes keep host numbering inside the container. The toolkit injects the dGPU as the host numbered it, so on a host where the dGPU is renderD129 there is no renderD128 in-container at all.

When the host has two GPUs, everything picks the wrong one

This is the cluster of problems that will bite next, and it is the same hardware shape: biggs has an AMD iGPU beside an RTX 5090, ganyu has an Intel iGPU beside the 3090.

The networking lesson nobody expects

Of everything here, this is the one I would flag hardest, because Jory's setup matches the broken configuration exactly and nothing in his repo addresses it.

Sharing one LoadBalancer IP between the moonlight proxy and every per-session RTP Service via lbipam.cilium.io/sharing-key forces externalTrafficPolicy: Cluster — Cilium will not share an IP across Local-policy Services with different pod selectors (cilium/cilium#38766). Cluster policy advertises the VIP from every node, so Moonlight's high-bitrate UDP video can land on a node with no GPU and be SNAT-hairpinned to the streaming node.

That presents as packet loss, not as a routing error. It looks like an encoder or bitrate problem, which is the wrong place to spend an evening.

The fix keeps the shared IP and the Cluster policy and opts those Services into direct server return, so the video path egresses straight from the backend node with no extra hop or SNAT:

annotations:
  service.cilium.io/forwarding-mode: dsr      # needs bpf.lbModeAnnotation=true
                                              # + loadBalancer.dsrDispatch on Cilium

The annotation must be present when the Service is created, so biggs injects it with a MutatingAdmissionPolicy matching LoadBalancer Services in the namespace that carry the direwolf sharing key — the same admission technique used for the VRAM gate. Per-session RTP Services are created fresh each time and are covered automatically; the long-lived proxy Service has to be recreated once after the policy lands.

Two related details Jory already has right: the operator's --lb-sharing-key defaults to the pod namespace while the chart annotates direwolf, and a mismatch hands the session's RTP Service a different external IP than the proxy so the RTSP handshake to the paired address times out (macOS errno 60) — his is aligned. And the shared VIP itself is pinned, so the group does not drift across the pool on recreation.

Things that only matter once Steam is the target

  • Privileged app container. Wolf hotplugs uinput devices mid-session, and Kubernetes has no equivalent of Docker's device_cgroup_rules, so nothing else can open the late-appearing /dev/input/event* nodes.
  • A real systemd-udevd inside the container. Beyond the agent's fake-udev, Steam Input emulates a second uinput pad for the game; without an in-container udevd nothing writes its udev database entry, so SDL and Proton see no controller in-game.
  • user.max_user_namespaces > 0. Steam's pressure-vessel runtime requires it and Talos defaults it to zero — node-level configuration, not a manifest change.
  • 4Gi /dev/shm. The 64Mi runtime default is exhausted instantly by Steam's CEF UI, giving a black screen with only a cursor.
  • DLSS needs two things. The nonfree-kmod-nvidia extension strips the NVIDIA wine NGX bridge DLLs, so an initContainer extracts them from the matching driver .run and caches them on a PVC; and DLSS is gated behind NVAPI, so PROTON_ENABLE_NVAPI and DXVK_ENABLE_NVAPI must both be set or the in-game toggle stays greyed out.

Two failures that share one root cause

Do not set NVIDIA_DRIVER_CAPABILITIES on the app container, and do not re-declare PUID/PGID/UNAME on the wolf sidecar. The operator already appends the former, and env is a listType=map keyed by name, so a duplicate key makes the server-side-apply patch invalid — the session Deployment is never created and the reaper kills the session 60 seconds later. The symptom is a session that simply never starts, with nothing obviously wrong in any container log, because there is no container. Jory hit the second half of this and solved it with an entrypoint ConfigMap shim rather than env.

A negative result, recorded properly

The nvidia-gpu-tuning DaemonSet carries an unusually honest comment. Recurring Xid 109 (CTX SWITCH TIMEOUT) under UE5 and DX12 load was chased with clock caps at 2850, 2800 and 2600 MHz and a 450W power cap, and reproduced at all of them — including at roughly 6% GPU utilisation and 82W, which rules out power, voltage and thermal transients. The recorded conclusion is that no nvidia-smi lever fixes it and the Blackwell plus open-RM-module fault needs a driver or vBIOS update.

Two things follow. That failure is 5090-specific, so neither Jory's 3090 nor a 5070 Ti inherits it. And the practice is worth copying independently of the finding: the record of what did not work, with the numbers that ruled it out, lives in the manifest that holds the tunable, where the next person to reach for that lever will actually read it.

The order I would attack it in

  1. Get the session pod onto the NVIDIA runtime — runtimeClassName or node default, per section two. Nothing below can be evaluated until driver userspace is injected.
  2. Make Test Ball and Firefox agree on renderD129, so a software-x264 fallback cannot be mistaken for success.
  3. Run Test Ball. Video means the encode and transport path is sound and the problem is compositor and EGL; no video means injection or transport.
  4. Run Firefox, adding GBM_BACKENDS_PATH to the app container as well as the sidecar.
  5. Apply the DSR policy before judging stream quality. Hairpinned UDP looks exactly like an encoder problem and will send you back to step three for no reason.
  6. Steam last, with VK_DRIVER_FILES, the privileged container, the shm bump and the node-level user-namespace setting.

04Gate the session, do not merely preempt the model

Gate the session, do not merely preempt the model

The second thing biggs.dog has that this cluster does not is a purpose-built arbiter — shrinedogg/gpu-arbiter-operator, a cluster-scoped GPUArbiter CRD. It exists because a PriorityClass solves the wrong half of the problem.

The arbiter also runs the other half — while any gaming pod exists it holds the inference Deployment at zero, and restores it when the session ends. That is a graceful scale-down rather than a SIGTERM eviction, and it is what makes the handover symmetric.

Adapting it here has one real obstacle

The arbiter scales a Deployment. llama-nvidia is an llmkube InferenceService that declares replicas: 1, and an external controller writing replicas on a resource an operator owns is a known way to produce a fight — cogito has already had to fix exactly that class of bug between Flux and ModelPool. The clean adaptation keeps both mechanisms in their lane: leave the PriorityClass to free the pod, and use the gate only to hold the session until the VRAM is demonstrably back. That needs the MutatingAdmissionPolicy and the DCGM half of the arbiter, and none of the scaling half — and the DCGM exporter is already deployed on the eGPU node.

05Planning a second card that yields to games

Cogito's plan adds a node with a 5070 Ti and 16GB that defers to playing and streaming, exactly as ganyu's 3090 does. The mechanism transfers verbatim. What has changed is that the node no longer has a mandatory tenant: vLLM's continuous batching lets one Qwen endpoint on the two 3090s serve several agents concurrently, so a second local model is no longer needed to get a second lane. Muse Glimmer belongs here only if it is wanted for what it writes — and if it is, two things about its current configuration have to change first.

If Muse does come here, two things block it today

The weights are too large. The staged build is Muse-Glimmer-30B-KQuant-17GB-Q4_K_M.gguf — 17GB, on a 16GB card, before a single byte of KV cache or the speculative-decoding draft model. A smaller quant has to be sourced or built.

The KV configuration is not satisfiable at any size. The current InferenceService asks for contextSize: 200000 with cacheTypeK and cacheTypeV at f16. KV cost is 2 × layers × kv_heads × head_dim × bytes per token, so at f16 and 200k tokens that is tens of gigabytes for a 30B-class model — more than the whole card, and more than it has today on a 24GB 3090. Switch both to q8_0 to halve it, then size the context to what is actually left after weights. llama-server prints the KV allocation at startup; that is the number to read rather than estimate.

Section one transfers verbatim — a PriorityClass at value: -100 on the inference pod, and nothing at all on the gaming side. Four rules come with it:

  • Advertise no more GPU units than a session consumes. This is the trap. Jory's session takes 2 of 2 because Wolf claims the GPU twice — compositor and app. If the plugin on that node advertises four units and a session takes two, preemption never fires: the game and the model share the card and both suffer, which is the exact outcome the setup is meant to prevent.
  • Size the model to 16GB and to the interruption. Muse is a good fit for the second half of that requirement and a bad fit for the first: it is the creative and uncensored model, so an eviction mid-session costs a retry rather than a broken pipeline, but it needs a quant that leaves room for KV on a 16GB card. Nothing on the critical path belongs on a node that disappears when someone starts a game — and after this change the critical path is Qwen on the two 3090s, which stays put.
  • Never make it a bare fallback or tier target. A target that can vanish mid-request needs a target of its own behind it.
  • Keep its weights in the hot tier. Cogito's two-tier cache means a cold miss costs a LAN copy from the NFS archive; on a node that is preempted several times an evening, that is the difference between a warm restart and a visible outage each time.
  • Gate the game on free VRAM, not just on the pod being gone. Section four's arbiter applies directly here, and cogito already runs a DCGM exporter. Preemption deletes the inference pod synchronously but the driver releases its framebuffer asynchronously, so a session that schedules immediately can find the memory still held. A MutatingAdmissionPolicy that gates game pods at CREATE plus a small controller that ungates on a DCGM free-VRAM threshold — with a bounded timeout so a stale metric degrades to starting anyway — closes that window. Take the gating half only: the upstream arbiter also scales the inference Deployment, and writing replicas on a resource llmkube owns is the same fight already fixed between Flux and ModelPool.

The prerequisite nobody will notice is missing

Cogito's routerSettings declares no fallbacks at all. On a swap pool that was defensible — there was nowhere to fall back to. With a preemptible node in the mix, an evicted model means a failed request with no escape path, and the eviction is silent and routine. If anything at all is placed on the 5070 Ti, the per-role fallbacks the routing teardown §11 now specifies — worker → worker-escalated, and a target behind every alias this node backs — stop being an optimisation and become the thing that makes the node usable. The teardown's validator asserts exactly this.

The routing half of this — role aliases, per-role virtual keys, and why the coordinator must not carry a cross-provider fallback — is in the routing teardown. Two things matter here. A node that disappears mid-request needs something behind it — the role fallbacks above, now that the teardown declares them. And whatever lands here should evict as one schedulable tenant: the utility roster The Idle Bench §3 plans (a compact VLM, a Muse re-quant, Whisper, an optional heavy reranker) ships as a single pod holding the node's whole advertised budget, so a session preempts everything at once instead of leaving survivors sharing the silicon — §3 there covers why the scheduler's minimal-preemption behaviour forces that shape. Unavailability during a session is an acceptable answer for creative and auxiliary models, and never for a worker or the retrieval floor — which is why the two 3090s keep the critical path and the embedder lives on kristeva's A380, not here.

06The to-do list

The gaming node — deliberately last in the serial plan: nothing on the critical path waits for it, and every prior list leaves it a clean slot to land in.

  1. Swap the machines.
    • The desktop joins the cluster; the laptop becomes the daily driver and Moonlight client.
  2. Provision the Talos node.
    • NVIDIA extensions and runtime class, with the device plugin advertising exactly two units — the number a Wolf session consumes.
  3. Ship the utility roster as one pod at priority −100.
    • A single pod requests both units so eviction is all-or-nothing (The Idle Bench §3's rule); verify a synthetic default-priority claimant actually preempts it before anything else lands.
  4. Bring up Wolf by the bisection ladder (§3).
    • Runtime class on the session pod first — nothing downstream is testable without injected driver userspace.
    • Agree every App on the dGPU's render node, then Test Ball, then Firefox with GBM_BACKENDS_PATH on both containers, then Steam with the Vulkan pinning, shm, and userns items.
    • Apply the DSR annotation before judging stream quality — hairpinned UDP impersonates an encoder problem.
  5. Gate sessions on free VRAM (§4).
    • MutatingAdmissionPolicy at CREATE plus a DCGM-driven ungate with a bounded timeout, taking the gating half of the arbiter only.
  6. Source the Muse re-quant.
    • Small enough to leave real KV headroom on 16GB before it joins the roster; fix the 200k-context KV config it inherits.
  7. Confirm the fallbacks.
    • The routing teardown's validator asserts a target behind every alias this node backs — run it as the node's acceptance check.
