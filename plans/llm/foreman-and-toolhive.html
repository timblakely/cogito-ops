01Three systems, one connector

Nothing in this loop is hand-run. Issues are the input, merged PRs are the output, and a human appears exactly once — at merge.

SystemJobLives in Git as
DispatchAssignment layer and system of record. Pull-only: it syncs tracked repos, grooms issues into lanes, and watches PRs.llm/dispatch/ — HelmRelease + ExternalSecret
ForemanExecution layer. An LLMKube add-on control plane shipping the Workload, AgenticTask, Agent and FleetNode CRDs.llm/foreman/ — operator + 7 Agent CRs
foreman-dispatch-bridgeThe only thing joining them. A CronJob on */15 that retries failed Workloads, then claims one ready issue per lane and materialises a Workload.llm/dispatch/foreman-dispatch-bridge/

The split matters for what is committed. Workloads, AgenticTasks and FleetNodes are ephemeral runtime state and never land in Git; the durable configuration is the bridge's env block and the Agent CRs. So the repo describes the machine, not the work in flight.

02Issue to merged PR

Two details in the Workload are load-bearing. The coder agent is picked from the lane's list by issue % len(list), which is deterministic — so a retry lands on the same backend and reuses its warm prompt cache. And the issue number is carried on the Workload itself; a bridge version that dropped it on retry collided every third attempt onto a shared wl-<repo>-0 branch that retries then force-pushed over.

03The agents, and what they run on

Seven Agent CRs are committed. Every one authenticates to LiteLLM at http://litellm.llm:4000/v1 with the foreman virtual key, whose scope is exactly three model groups — llama-nvidia, MiniMax-M3-chat, llama-strix-nemotron. The key is the enforcement boundary: an agent pointed at any other model would be refused by the proxy, not by the operator.

Coders differ only by model. Same image, same tools, same prompt skeleton: ghcr.io/misospace/llmkube-coder, one polyglot image carrying Python, Node, Go, Godot headless and Elixir plus every linter. Rootless coders cannot install anything at runtime, so every runtime is baked in. Four per-language images and four per-language agents were collapsed into this in 2026-08, on the reasoning that they differed only by a prompt paragraph restating the gate commands — and the genuinely load-bearing part, repo-specific traps, is repo knowledge that moved into each repo's AGENTS.md.

Two fleets, one of them pointed at its own operator

The HelmRelease defines two foreman-agent fleets:

FleetReplicasRolesIdentity
default7worker · coder · verifiercommits as Saffron, a bot account
llmkube1coder-fork · verifier-fork · reviewer-forkclones and pushes joryirving/LLMKube, commits as Jory with DCO sign-off

The second fleet exists to run the whole pipeline against a fork of LLMKube itself and open cross-repo PRs upstream into defilantech/LLMKube. Roles are scheduling-only, so the separation is what keeps ordinary work off the fork-pinned agent and vice versa — and the author identity differs because upstream requires a real signed-off contributor rather than a bot. An agent fleet whose job is submitting patches to the operator that schedules it is a nice loop to have closed.

Documentation drift

The repo's own docs/src/notes/coding-loop.md describes a coder-strix agent on a self-hosted pool, a Mellum2-based reviewer, and replicaCount: 12. None of those match the manifests at this commit: there is no coder-strix, no self-hosted model group, the reviewer runs Nemotron, and replicaCount is 7. The prose is still the best explanation of why the machine is shaped this way; treat its specifics as a previous generation.

04Fleet capacity is agent replicas, not models

This is the least obvious constraint in the whole system, and the one that produced the worst outage. Foreman enforces one task per FleetNode, and one FleetNode is one foreman-agent replica. A Job-mode task still reserves its node for the Job's entire lifetime even though the work happens in a separate pod.

05The reviewer is not trusted — it is grounded

The most transferable idea in this repo: a local 30B model's verdict is checked by deterministic rails before it counts, so the model's job is to produce evidence rather than a judgement.

The reviewer agent is read-only by construction — its tool whitelist is read_file, grep, bash, fetch_issue, fetch_pull_request, submit_result. No write_file, no str_replace. It describes needed changes in its verdict; it cannot edit the branch.

Then the harness checks its work. submit_result must carry:

FieldWhat it must containRail
extra.issueAskOne exact contiguous quote (≤200 chars) from the issue body, stating the requested change — not the backgroundGrounded against the issue body the harness saw fetched. A quote it cannot find is replaced and marked unverified, and an unverified GO is demoted to NO-GO
extra.filesTouchedThe exact path list from git diff --name-only main...HEADFeeds the scope-overlap vouch that can waive a demotion
extra.findingsArray; every blocker or major finding must name a file and a line changed by the diffA GO may carry no blocker or major finding
extra.prBodyFull Markdown PR description, GO onlySince 0.9.15 the summary is itself grounded against the diff

The consequence runs backwards into how issues must be written: an issue that cannot be quoted gets correct work rejected. So every filed issue carries one imperative sentence stating the ask, plus the concrete paths the fix should touch — and the trap is that naming paths the diff does not touch reads as scope drift and rejects the change too, so the guidance is to name none rather than guess. Each repo carries that contract in its AGENTS.md and as an issue form.

The rails are imperfect in a documented way: LLMKube#1447 records the reviewer false-NO-GOing test-coverage issues, where the diff touches X.test.ts and the issue names X.ts, and #1454 records a reviewer that says “cannot verify” still returning GO. The prompt itself carries the scar tissue — it tells the reviewer, at length, not to rely on the vouch and to re-read the body before submitting.

06Gates: the coder verifies its own work

Clean-room verify Jobs are off (VERIFY_ENABLED=false); the repo's own CI is the verifier. In between, the coder runs the repo's gate profile on itself before submitting — format, lint, build, test — from a per-repo GATEPROFILE_MAP carried as one large JSON env on the bridge, with container image digests inside it managed by a custom Renovate regex manager.

"misospace/pinchflat": {
  "testLayout": {"testRoot": "test", "sourceRoot": "lib"},
  "language": "generic",
  "image": "ghcr.io/misospace/elixir-gate:1.20.3@sha256:1c9837c6…",
  "commands": {
    "format": "true", "lint": "true", "build": "true",
    "test": "mix deps.get && … && mix check --no-fix --no-retry"
  }
}

The rule Jory states, both halves earned: a gate profile must mirror what CI actually runs — no more, no less. A check CI runs but the gate does not is a blind failure the coder discovers only after pushing, costing a pr-fix cycle. A check the gate runs but CI does not is worse, because it fails work that would have passed — a mix deps.audit added before the repo carried mix_audit broke every task on that repo until reverted.

The failure that motivated the polyglot image

The self-gate silently no-ops when its runtime is missing, logging self-gate-deferred and deferring to a backstop that is disabled. With no Godot in the coder image and no gate Job, a test file that did not parse shipped — and the reviewer GO'd it anyway. One image containing every runtime is what makes the gate profiles actually execute.

07The pr-fix loop and its guard rails

Dispatch watches PRs authored by the bot identities and enqueues a fix item on real signals only: a CHANGES_REQUESTED review (it trusts the verdict, not keyword-matching the prose), failing check runs, or comments carrying actionable signal or an @-mention. Chatter, CI tables and status posts are ignored regardless of author.

The bridge drains queued items into prfix-<repo>-<pr> Workloads; the coder checks out the existing foreman/* branch and amends it. Lane NORMAL → coder; after three attempts → ESCALATED → coder-frontier; exhausted there → BLOCKED, which means a human.

GuardWhat it stops
No check runs ≠ passing CIA GitHub Actions outage marking unverified fixes as FIXED, then force-push loops
Merged or closed PR → resolve, never retryThree attempts plus a frontier escalation burned on an already-merged PR
Duplicate evidence keeps item statusAn undismissed review resurrecting resolved items on every sweep

Each of those is dated to the release that added it, which is the tell that they were paid for in outages rather than designed up front. The same discipline shows in the failure taxonomy: a coder can declare DESIGN-DECISION or NO-TECHNICAL-FIX and be parked for a human without burning an attempt, and a Failed Workload is explicitly not treated as proof the model failed — one night's four failures audited out as two merged-PR retries, one closed-issue tombstone, and a single real one.

08ToolHive: MCP servers as cluster workloads

ToolHive (toolhive.stacklok.dev) turns each MCP server into a Kubernetes object. Nine tool sources are registered into a single MCPGroup named mcp-tools, in two kinds:

KindServersWhat it means
MCPServerflux · kubectl · talos · github · ha · arr · seerr · unifi-networkToolHive runs the container itself — image, transport, proxy port, resources, ServiceAccount
MCPServerEntrygrafanaRegistration only, pointing at an existing service elsewhere in the cluster (mcp-grafana.observability:8000/sse)

Because they are pods, the cluster's ordinary controls apply to them. The infrastructure servers carry real RBAC rather than a shared admin credential — kubectl-mcp binds a read-only ClusterRole enumerating nonResourceURLs explicitly, talos-mcp gets a Talos ServiceAccount, flux-mcp runs in-cluster mode off its pod ServiceAccount with no kubeconfig at all. Credentialed SaaS servers get an ExternalSecret each. A single MCPTelemetryConfig turns on Prometheus for all of them.

09The tool optimizer, and the loop back to the LLM stack

Nine MCP servers is well past the point where dumping every tool definition into an agent's context is affordable. The VirtualMCPServer is the answer, and it is the most interesting object in either repo.

Two exposures, deliberately different. Internally the gateway is vmcp-mcp-gateway-internal.llm:4483 with incomingAuth: anonymous — in-cluster callers are already inside the trust boundary. Externally the same service is published at mcp.jory.dev behind an Envoy SecurityPolicy enforcing x-api-key with sanitize: true, so the credential is stripped before the request reaches the gateway. Outgoing auth to each backing server is discovered rather than configured centrally.

The cross-stack dependency worth knowing

toolhive-embed is an llmkube InferenceService claiming the shared llama-strix-gpu template on skirk, and it is reached through LiteLLM. So the tool gateway, the coding agents and the chat models all terminate on the same two pieces of infrastructure. That is efficient, and it means a skirk outage takes out inference and tool discovery together — the failure modes are correlated in a way the component diagram does not show.

10Foreman is a coordinator — with the reasoning taken out

Read structurally, this is already a coordinator-and-subagent system. What sits in the coordinator slot is a CronJob, an operator and a lane table rather than a model that thinks.

The division of labour is the same one a reasoning coordinator would impose. Something decides what work exists, decomposes it into tasks, binds each task to a model chosen for that role, reads the outcome and decides what happens next. Here that something is deterministic: Dispatch grooms, the bridge claims and builds a Workload, the operator decomposes into code → review, and escalation is an attempt counter. The models only ever do leaf work.

Deterministic coordinator — Foreman todayReasoning coordinator
DecompositionFixed pipeline: code then review, identical for every issueAdapts to the task; can split one request across two models
EscalationAttempt counter — 3 failures re-lanes to frontierJudgement after reading the output, not after counting
ObservabilityCRs, lanes and audit ConfigMaps — inspectable with kubectlA conversation; legible to a person, harder to query
Failure modeWrong lane, stuck Workload — visible and boundedA confused coordinator retrying at cloud rates — bounded only by caps you impose
Guardrails neededRails on leaf output, because nothing above the model is judgingRails on leaf output and turn plus spend caps on the coordinator
Cost profileCoordination is free; all spend is leaf workCoordination is the expensive per-token component, but low volume

The trade is legibility for adaptability. A fixed pipeline cannot notice that an issue needs a design conversation before any code is written — which is why Foreman has a DESIGN-DECISION escape hatch that parks the task for a human instead. A reasoning coordinator would handle that case, and in exchange its own reliability becomes the system's reliability.

What carries over either way

Four mechanisms in this repo are properties of the shape, not of the deterministic coordinator, and they transfer unchanged to a reasoning one:

  • Bind a model per role in configuration, not in prompts. Agent.providerConfig.model is one field per role; swapping which backend does review is a one-line change that touches no prompt text.
  • Let the virtual key be the enforcement boundary. The foreman key permits exactly llama-nvidia, MiniMax-M3-chat and llama-strix-nemotron. A mis-set model fails at the proxy rather than quietly billing a frontier provider — a property worth more, not less, when a reasoning coordinator is choosing delegates dynamically.
  • Ground leaf output deterministically. The verbatim issue quote, the path list from the real diff, the file-and-line anchor on every finding. A coordinator that trusts a subagent's self-report inherits exactly the failure the demotion rule exists to catch.
  • Bound the leaf. maxTurns of 160 for coders and 80 for reviewers, plus context soft and hard caps and stuck-loop detection. Delegation without a turn cap is an open-ended bill.

And the chat stack in the same cluster has already taken the other branch: openclaw runs a high-thinking coordinator with spawn rights, a restricted low-thinking worker, cloud subagents at maxConcurrent: 3, and an hourly heartbeat pinned to a local model in an isolated session. That topology, and what it implies for a cluster whose local capacity is dedicated rather than shared, is in part one, section thirteen.

11What transfers

Setting aside whether one wants an autonomous coding loop at all, four ideas here are worth stealing independently of Foreman:

  • Ground the model's verdict, don't trust it. Requiring a verbatim quote from the issue, a path list from the real diff, and file-and-line anchors for every finding turns “did the model review this properly?” into an assertion the harness can check. The demotion rule — unverified quote turns GO into NO-GO — is what gives the requirement teeth.
  • Decide tiering by failure, not prediction. The groomer answers only ready/not-ready; nothing reaches a paid model until local attempts have actually failed. Compare the complexity router in part one, which predicts difficulty per request and is currently mis-wired — this loop reaches the same cost goal with no classifier at all. Across a cloud-and-local boundary that argument gets stronger, which is why part one now proposes a coordinator rather than a router.
  • Make the silent no-op loud. A self-gate that skips when its runtime is missing shipped a test file that did not parse. Any check that can quietly do nothing will eventually do nothing at the worst moment.
  • Scope credentials at the proxy. The foreman virtual key allows exactly the three model groups its agents use, so a mis-set Agent.providerConfig.model fails at the proxy instead of quietly billing a frontier provider. The same mechanism is what the missing-model validator in part one would harden.

And one caution that applies to both halves of this cluster: the durable configuration is spread across an Agent CR, a HelmRelease values block, a large JSON env on a CronJob, a virtual key's scope, and a prose note in docs/ that has already drifted from the manifests. Every one of those is a place a name can be wrong without anything erroring.
