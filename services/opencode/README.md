# Cogito OpenCode host

Cogito is a separate host in the laptop Paseo client, not an OpenCode provider
attached to the laptop daemon. Local Hermes remains on the laptop host.

```text
Laptop Paseo client -- HTTPS/WebSocket --> paseo.timblakely.com
                                          |
                                    Paseo daemon :6767
                                          |
                                    OpenCode :4096
                                    localhost, same pod
                                          |
                                      /workspace
```

Both containers run on kristeva with uid 1000 and share the existing
`opencode-home` and `opencode-workspace` claims. Paseo's persistent state is
`/home/opencode/.paseo`; both claims retain their hourly Kopia backups.
There is no laptop mount, path alias, callback, port forwarder, or relay.

## Connection and authentication

Add `paseo.timblakely.com`, port 443, SSL enabled, as a direct host in Paseo.
The host password is `op://kubernetes/paseo/server-password`. It is generated by
External Secrets, pushed to 1Password, and passed through `PASEO_PASSWORD`.
The internal gateway terminates TLS. Do not put Pocket ID OIDC on this route:
Paseo's API and WebSocket require the native password flow, not browser redirects.
The existing OpenCode browser dashboard retains its separate Pocket ID route.

The laptop should not configure `PASEO_OPENCODE_SERVER_URL` for this deployment.
Only the cluster daemon points to `http://127.0.0.1:4096`; its bridge callback
uses loopback in the same pod. `paseo-opencode-bridge-forwarder.service` and the
old `opencode-lan` HTTPRoute are obsolete.

## Image and bootstrap

The child image pins OpenCode and Paseo, and generates Paseo's official bridge
from the installed server package during the cluster-local build. Init copies
that artifact and the managed Paseo configuration to the home
claim before either daemon starts. A fresh home claim therefore does not need
manual bridge installation. User sessions, host identity and repositories remain
persistent state; init never clears them.

The home-ops toolset in `packages.txt` includes Git/jj, Bash, ripgrep, curl,
GNU coreutils, jq, Mike Farah yq, yamlfmt/yamllint, ShellCheck/shfmt, Helm,
Kustomize, Flux, GitHub CLI, SOPS/age, Python/PyYAML/pip/uv, Node/npm, just,
SSH/rsync, DNS/network diagnostics, archive utilities, and GCC/G++/make.
Kubectl is checksum-verified and pinned to 1.34.2 to match the cluster instead
of taking Alpine's newer, out-of-skew client. Mise 2026.11.13 is copied from
its digest-pinned static image; project tools can be installed as uid 1000
under the persistent HOME. Use `mise exec` for noninteractive project commands,
trust only intended configurations, and keep tool versions/locks in each repo.
No kubeconfig, GitHub token, SOPS private key, Rust toolchain, or CUDA is baked in.
Installing administration binaries does not grant deployment authority or change
OpenCode's existing permission policy.

GNU env fixes the upstream Paseo launcher's `env -S` requirement on Alpine.
The sidecar's explicit Node command remains compatible. `/opt/opencode-apk-packages.txt`
records the resolved OS package versions; OS indexes and npm transitive packages
are not fully locked, so a clean rebuild may have a different digest. Pin the
published artifact, not a claim of byte-identical rebuilds.

## LAN-only image builds

Images live only at `registry.timblakely.com/timblakely/opencode-cogito`.
The manual builder (`kustomization.yaml` plus `build/`) is outside the Flux app tree:
publishing this recipe does not start a build. It runs on kristeva, requests no
GPU, mounts no user/model workspace, and pushes directly to Zot over the LAN.
Only the small recipe is sent from the workstation; downloads go to the builder
and image layers never upload to a public registry. GitHub Actions performs
source checks only, with no image build or package-write permission.

From the repository root:

```sh
kubectl kustomize services/opencode > "$TMPDIR/opencode-build.yaml"
kubectl apply --dry-run=server -f "$TMPDIR/opencode-build.yaml"
kubectl apply -f "$TMPDIR/opencode-build.yaml"
kubectl -n cluster-infra logs job/opencode-image-build
```

The Job has a one-hour deadline, no retries, 4 CPU/8Gi limits, and a dedicated
25Gi Ceph build cache. Privileged BuildKit is a deliberate trust decision; its
RUN workers are placed under the same finite Pod cgroup (Guaranteed or Burstable
QoS), rather than escaping limits into host-root cgroups. It has no Kubernetes
service-account token and only the existing `registry-build-auth` push credential.
Do not reuse it for untrusted Dockerfiles. Image build runs `opencode-image-check`
as uid 1000 and fails before publication if the tool smoke test fails.

To rebuild, first confirm the previous Job has finished, then delete only
`job/opencode-image-build` and reapply the render. Keep the cache PVC. Recipe
ConfigMaps are content-addressed; do not alter a running build's inputs. Tags
use a recipe-content hash (`homeops-<hash>`) covering the image inputs, builder
script/config and Job definition; the full hash and source URL are OCI labels.
Upstream package changes can
produce a new digest for the same recipe tag. Always deploy by digest. A completed
Job prints `PUBLISHED_IMAGE` and BuildKit's `containerimage.digest` metadata.

Verify the exact published digest with the namespace-local pull credential:

```sh
python3 services/opencode/build/verify.py registry.timblakely.com/timblakely/opencode-cogito:homeops-<hash> --expected-digest sha256:<digest>
```

A fresh uid-1000 Pod should pull that digest with `opencode-registry-pull`, a
read-only root filesystem and writable HOME/tmp/workspace, then run
`opencode-image-check`. The pull Secret is supplied by External Secrets from
`registry-template/PULL_PASSWORD`; the builder credential is never mounted into
OpenCode. The shared HelmRelease image anchor covers init, OpenCode and Paseo.
Validate its change with `flux build kustomization opencode -n llm --path
./kubernetes/apps/llm/opencode/app`, server dry-run, Helm render and targeted
flux-local tests before publishing through jj. Check for active Paseo turns
before rolling the pod.


## GitHub repository authentication

The managed Git HTTPS helper authenticates only
`https://github.com/timblakely/cogito-ops` (with or without `.git`). External
Secrets issues a dedicated GitHub App installation token for `cogito-ops` with
only `contents: write`, refreshing it every 30 minutes. The existing App key is
sourced from `matrix-github-app/private-key` in 1Password into a separate
`opencode-github-app-auth` Secret for the generator. That private key is never
mounted into OpenCode; neither is Foreman's broader token.

Only the main container mounts `opencode-github-token`, read-only at
`/var/run/secrets/github/token`, with a directory mount rather than `subPath`.
The system `/etc/gitconfig` enables `credential.useHttpPath` and invokes the
managed Python helper, which reopens the projected token on each authentication
request and ignores credential store/erase operations. It rejects other hosts,
protocols, repository paths and conflicting usernames. A missing or malformed
token fails closed without printing its contents. No token is baked into the
image, copied into the persistent home/workspace, or supplied through `GH_TOKEN`
or other environment variables. `gh` API authentication is not configured by
this helper. Use the HTTPS origin, not an SSH remote.

Global/repository config takes precedence over this system default. A later
empty `credential.helper` reset or `credential.useHttpPath=false` can disable
the scoped helper. Verify the effective helper list and path setting in the
actual checkout, not just the mounted system file.

The installed jj 0.42 uses Git subprocesses for remote transport, so
`jj git fetch` and `jj git push` use the same helper without a separate jj
credential setting. Credential scope is not a sandbox: the trusted agent's
shell can read the mounted token. GitHub enforces the token's repository and
permission scope; it does not enforce branch-specific publishing approval.
Issues, pull requests, Actions and workflow-file changes are not granted.

The generated token Secret carries `reloader.stakater.com/ignore: "true"`.
This is essential: OpenCode otherwise auto-reloads for mounted Secret changes,
interrupting active turns every 30 minutes. Kubelet projects the rotated file
without a restart (not instantaneously); all other credential/config reloads
remain enabled. Expired tokens or failed generator refreshes still fail auth;
do not work around them by persisting a token in a checkout.

Before the first rollout, render and server-dry-run the app. From an already
authenticated workstation, bootstrap just the two GitHub ExternalSecrets and
their generator from that render, then wait for both ExternalSecrets to become
Ready and the token Secret to be nonempty. Only then publish the mount change
through jj/Flux; a single ungated push can roll the consumer before its Secret
exists. Check for active Paseo turns before changing the pod's mounts. After rollout,
verify the final pod's mount permissions as uid 1000, no token environment
variable or private-key mount, and the Secret's Reloader ignore annotation.
Prove write authentication without changing refs by fetching the repository's
HTTPS `info/refs?service=git-receive-pack` advertisement with credentials from
the helper held only in process memory; compare authenticated success against
unauthenticated rejection. Also run `jj git fetch` in an appropriate checkout.
`jj git push --dry-run` only displays a local plan and does not test remote
authentication. If jj author identity is unset, configure the intended
`user.name`/`user.email` before authoring changes; authentication does not set
commit attribution. A real push to `main` deploys Cogito and needs the normal
task authorization. Observe a subsequent token refresh and unchanged pod UID
to verify rotation without a session restart.

## Cluster operations

The OpenCode pod uses `llm/opencode-reader`, not an administrator kubeconfig.
Its mounted kubeconfig references the projected service-account `tokenFile`, so
client-go rereads rotating credentials. `kubectl` can read resources across the
cluster, read pod logs, watch changes, query metrics, and port-forward. Secret
contents, exec, node proxy and direct resource mutation are not granted.
Port-forward deliberately requires `create pods/portforward`; the resulting
localhost listener is inside the OpenCode pod, not on the laptop.

Managed OpenCode MCP server `flux` connects to ToolHive's internal
`mcp-flux-ops-proxy.llm.svc.cluster.local:8080/mcp`. A small stdio/HTTP transport
adapter uses the MCP SDK already in the image and rereads the reader identity
on each HTTP request; no static token, cached authorization header, new image
build, or laptop callback is needed. Request failures return JSON-RPC errors
without killing the relay or blindly replaying potentially completed writes.
If authentication fails, verify `kubectl get --raw /.well-known/openid-configuration`
reports the issuer pinned in `toolhive/flux-ops/auth.yaml`. The proxy authenticates Kubernetes JWTs
and authorizes only the reader subject. NetworkPolicies restrict proxy ingress
to OpenCode and backend ingress to the proxy. A ValidatingAdmissionPolicy
additionally denies this reader's port-forward/exec/attach requests into all
ToolHive-labelled pods: kubelet tunnels bypass NetworkPolicy. Its Pod-parameter
selector follows generated pod names instead of relying on a StatefulSet ordinal.
The HTTP transport supports independent clients; Flux's stdio session rejects
multiple initializes and cannot be used as a shared backend here.
Neither component has a public route. Port-forward itself is not a read-only
security primitive: it may reach a target application's privileged localhost
listeners. The direct mutation restriction refers to Kubernetes API RBAC, not
the behavior of every application reachable over a tunnel.

The Flux MCP backend alone holds `llm/opencode-flux-operator`. It can
apply/patch/delete ordinary workloads, ConfigMaps, Services, PVCs, service accounts,
ingress/network policies, and Flux sources/Kustomizations/HelmReleases. It also
manages these namespaced application CR instances: ExternalSecret/PushSecret,
Envoy SecurityPolicy, PocketIDOIDCClient/PocketIDUserGroup, and Kopiur
Repository/SnapshotPolicy/SnapshotSchedule/Snapshot. Managing CR instances is
not CRD-definition administration. It supports reconcile and suspend/resume
through the upstream Flux MCP tools. Direct RBAC, Secret, TokenRequest, node,
namespace, PV, CRD-definition, cluster credential store and database
administration are not granted; the direct reader identity is unchanged.
These are operational credentials, NOT a sandbox: workloads, Flux inputs,
ExternalSecrets and identity/backup controllers confer substantial indirect
credential and data authority. MCP is the credential/transport boundary, not
protection from an authorized agent's misuse. Only use this host for trusted
projects and instructions.

Operational cleanup must check external identities, not just Kubernetes names.
Cross-namespace PushSecrets can overwrite the same vault field; verify
`deletionPolicy: None` before removing a duplicate exporter. Duplicate Pocket ID
CRs can own the same remote client/group: normal finalization may delete the
working application's identity. Orphan shared remote objects instead. Before
removing backup owners, stop their schedules and retain snapshots; deleting a
Snapshot CR with `deletionPolicy: Delete` can delete the actual backup. Never
strip storage/identity finalizers merely to make cleanup green.

Persistent changes still belong in the repository and go through `jj` and Flux;
the MCP path supports operational changes and temporary diagnostic/experiment
workloads without pretending everything must first be committed. GPU workloads
remain separate from the interactive pod; do not preempt/delete gaming pods.

Run `python3 -m unittest discover -s services/opencode -p 'test_*.py' -v`
with PyYAML 6.0.3 installed for static policy/config checks. Live acceptance must
also exercise reads/logs and a real tunnel, reject direct writes and unauthenticated
or wrong-subject MCP calls, confirm backend and proxy tunnel requests are
rejected by admission while normal diagnostic tunnels still work, apply/patch/delete disposable resources through MCP,
and request and observe a Flux reconcile. Prove tool use through a real Paseo
session, not just a direct MCP handshake.

## Models

OpenCode v2 does not discover models for a custom `openai-compatible` provider,
so every usable model is declared by hand in the system ConfigMap
(`kubernetes/apps/llm/opencode/app/opencode-config.yaml`). Two provider blocks
share the one LiteLLM gateway and each reads its own virtual key, so the two
scopes stay disjoint:

| Block | Package (transport) | Key | Scope |
| --- | --- | --- | --- |
| `cogito` | `openai-compatible` (chat completions) | `role-opencode` | the four local chat aliases |
| `cogito-sub` | `openai-compatible/responses` | `role-opencode-subscription` | the eight ChatGPT subscription aliases |

The split is forced by the catalogue, not taste: every subscription alias is
registered `info.mode: responses`, so a chat-completions route cannot carry it.
Adding a model therefore means editing the matching `models` map **and** the
matching `LiteLLMVirtualKey`, and running the admin `/key/update` afterwards —
the operator does not push an edited scope onto an already-issued key.
Subscription usage reports as zero-dollar spend, so a key budget does not
throttle that block; `maxParallelRequests` does.


## Verification

A provider diagnostic alone is insufficient. From the laptop, select the Cogito
host and start an OpenCode session in a cluster workspace using
`cogito/flashnext-deleuze`, then repeat the check with a `cogito-sub/*` model so
the Responses transport is proven and not merely configured.
Verify a tool reads cluster files and the turn completes through Paseo. Confirm
native unauthenticated access is rejected, both containers are Ready on kristeva,
Flux applied the published revision, and local Hermes remains available.

Repository checkouts are cluster-owned. Public repositories can be cloned with
`jj git clone`; the managed GitHub credential applies only to `cogito-ops`.
Agent permission rules are approval policy, not an OS security boundary.
