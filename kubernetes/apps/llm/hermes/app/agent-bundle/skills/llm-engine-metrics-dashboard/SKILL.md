# LLM engine metrics in Grafana

## When to Use

Building or editing a dashboard panel for prompt-processing speed, generation
speed, concurrency/slots, or KV-cache usage/hit rate of served models; or
answering "why doesn't LiteLLM show X" for any of those four.

## Core fact

Per-model prompt-processing speed, generation speed, concurrency, and KV-cache
usage/hit rate exist ONLY at the inference engines. LiteLLM's `/metrics` has
none of them (verified v1.97.0, 81 families): `litellm_in_flight_requests` is
per-uvicorn-worker HTTP concurrency with no model label, and its
`*_cached_tokens` counters are provider-reported usage accounting, not KV
occupancy. Do not keep looking for these in the proxy.

In cogito the `llmkube-inference` PodMonitor already scrapes all engine
families; the dashboard is `llm-serving.json` (see
`kubernetes/apps/llm/llmkube/app/grafanadashboard.yaml` for the full rationale
header), generated by `scripts/llm/build_llm_serving_dashboard.py` and checked
against live Prometheus by `scripts/validate-grafana-dashboard.py`.

## Pitfalls

- Never trust `runtime` for engine identity: it reads `generic` whenever an
  InferenceService overrides container args, for llama.cpp and Radiance alike.
  Discriminate by metric-family presence (`radiance:*` -> `llamacpp:*` ->
  `vllm:*`), with `unless on (service)` — Radiance re-exports the vLLM-compat
  surface and would classify as vLLM otherwise.
- llama.cpp `llamacpp:prompt_tokens_seconds` / `predicted_tokens_seconds` are
  per-scrape bucketed GAUGES that reset every scrape (`metrics.reset_bucket()`
  in server-metrics.cpp): `rate()` over them is always 0. Read them as instant
  values; use `*_total` counters for time series.
- llama.cpp prompt tokens EXCLUDE cache hits, so cache-hit ratios need
  `prompt + cached` in the denominator; the cache counter is
  `llamacpp:prompt_tokens_cached_total`.
- llama.cpp has NO KV-occupancy metric (`n_tokens_max` is the largest sequence
  ever seen, not usage) and NO TTFT metric at all. vLLM-compat histogram
  panels must not union llama.cpp series or their 0s pollute quantiles — put
  llama.cpp on a counted-seconds panel instead.
- Radiance's vLLM-compat surface covers TTFT, ITL, `kv_cache_usage_perc`,
  `gpu_prefix_cache_hit_rate`, preemptions — but NOT `request_queue_time_*`
  (use `radiance:http_queue_depth`) and NOT `cache_config_info` (use
  `radiance:kv_cache_max_tokens`).
- vLLM/Radiance `*_hit_rate` gauges reset per scrape: use the
  `prefix_cache_hits_total / prefix_cache_queries_total` rate ratio for history.
- `histogram_quantile` needs a `... and on (labels) rate(<metric>_count[...]) > 0`
  gate or idle series render NaN legends. Do not gate with `rate(bucket) > 0`
  on buckets — that drops legitimately-empty buckets and skews the quantile.
- `label_replace` must wrap `rate()`, never the other way around (`rate()`
  takes a selector, not an expression).
- PromQL regexes are FULLY ANCHORED and its string literals process escapes:
  `api_base=~"https?://lane[^/]*svc\\.cluster\\.local.*"` needs the `.*` tail
  (api_base continues `:8080/v1`) and a doubled backslash in JSON.
- LiteLLM's `requested_model` is NOT the lane name — catalogue aliases
  (`google/gemma-4-12b-it`, `Muse-Glimmer-30B`) differ from llmkube service
  names. Bridge via the deployment `api_base` hostname instead.
- Grafana `$var` cannot match a label that a query CREATES (`$lane` against a
  `label_replace`d `lane` silently returns empty); interpolate it INSIDE the
  selector regex. It works fine against scraped labels (`service`).
